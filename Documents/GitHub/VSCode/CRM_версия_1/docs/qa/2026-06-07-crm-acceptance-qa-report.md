# QA-отчет CRM перед передачей в работу

Дата проверки: 2026-06-07  
Проверяемый адрес: http://213.109.202.45/  
Метод: black-box проверка опубликованной CRM + grey-box сверка локальных исходников.  
Инструменты: Puppeteer/Chrome, HTTP-пробы, чтение acceptance checklist/API spec, три параллельных QA-потока.

## 1. Резюме

Текущая опубликованная версия выглядит как статический frontend-прототип на mock-данных, а не как готовая рабочая CRM.

Ключевой вывод: передавать систему менеджерам в боевую работу нельзя. Основные экраны открываются, визуальные карточки/таблицы/отчеты отрисовываются, но критичные бизнес-процессы не выполняются: нет работающего `/api`, нет реального сохранения сущностей, авторизация фиктивная, права доступа обходятся прямым URL, входящие webhook-заявки не принимаются.

## 2. Проверенное покрытие

Автоматический smoke:

- 38 desktop-страниц опубликованной CRM.
- 10 mobile-проверок на viewport `390x844`.
- API-пробы: `/api/auth/login`, `/api/clients`, `/api/reports/dashboard-owner`, `/api/webhooks/site-leads`.
- Интерактивные проверки: login, роль owner/manager, topbar create menu, command palette, уведомления, профиль, карточные вкладки, empty-state, настройки источников.

Потоки тестировщиков:

- Поток A: login, роли, shell, настройки, отчеты.
- Поток B: лиды, клиенты, сообщения, задачи.
- Поток C: сделки, КП, счета/закрытие, тендеры.

## 3. Критические блокеры

### B0-1. Backend/API на сервере не работает

Проверки:

- `GET /api/reports/dashboard-owner` -> `404 Not Found`
- `POST /api/auth/login` -> `404 Not Found`
- `GET /api/clients` -> `404 Not Found`
- `POST /api/webhooks/site-leads` -> `404 Not Found`

Ожидание: API должен отвечать JSON по спецификации `crm_project_docs/06_API_SPEC.md`.

Влияние: невозможно подтвердить авторизацию, сохранение, заявки с сайтов, роли, журнал действий, уведомления, интеграции.

### B0-2. Авторизация фиктивная

URL: `/app/login.html`  
Шаги: ввести любые данные или оставить поля пустыми, нажать `Войти`.  
Факт: пользователь попадает на `/app/dashboard-owner.html`, в `localStorage` ставится `crm.role = owner`.  
Ожидание: неверный пароль не должен пускать; успешный вход должен идти через backend/JWT.

### B0-3. Создание сущностей не сохраняет данные

Проверено: клиент, сделка, задача, КП.  
Факт: модалки могут открыться и закрыться, но записи не появляются в списках после перезагрузки; счетчики не меняются.  
Ожидание: сущность сохраняется в базе, появляется в списке, действие пишется в историю.

### B0-4. Создание лида отсутствует

Шаги: topbar `Создать` -> `Лид`, либо CTA на странице лидов.  
Факт: ничего не открывается. В исходниках для лида `modal: null`, файла `create-lead.html` нет.  
Ожидание: форма ручного создания лида и сохранение через API.

### B0-5. Webhook входящих заявок отсутствует

URL: `/api/webhooks/site-leads`  
Факт: endpoint отвечает `404`.  
Ожидание: CRM принимает заявки от сайтов, проверяет токен, создает лид, сохраняет сайт/URL/UTM, назначает менеджера и отправляет уведомление.

### B0-6. Права доступа не защищены сервером

Шаги: установить роль `manager`, открыть `/app/settings/funnels.html` напрямую.  
Факт: страница настроек открывается `200`, данные видны.  
Ожидание: менеджер не должен иметь доступ к настройкам; сервер должен блокировать прямой URL/API.

## 4. Функциональные дефекты UI

### Навигация и shell

- Мобильное меню не открывается: `[data-action="toggle-sidebar"]` не обрабатывается.
- На mobile есть сильный горизонтальный overflow: например dashboard owner `scrollWidth = 1119`, `innerWidth = 390`.
- `favicon.ico` отдает `404`.
- Кнопка профиля `Выйти` не выполняет logout и не ведет на login.
- `Завершить день` визуально меняет страницу/состояние нестабильно, но рабочая сессия не фиксируется через API.

### Лиды, клиенты, задачи

- Page-level кнопки `+ Клиент`, `+ Задача`, `+ Лид` на страницах списков не подключены.
- Фильтры `Источник`, `Ответственный`, `Статус`, `Дата`, `Приоритет` декоративные.
- Сегменты клиентов `Все/Юр.лицо/Физ.лицо/Госы` не фильтруют.
- Сообщения в карточке клиента не отправляются: ввод остается, новая запись не появляется.
- Быстрые действия в карточке клиента не открывают сценарии.
- Действия в строках задач не меняют статус.
- Календарь задач не переключает месяц стрелками.

### Сделки, КП, счета

- Кнопки `+ Сделка`, `+ КП`, `+ Тендер` на страницах списков не работают.
- В таблицах сделок/КП/тендеров нельзя открыть запись через строку или иконку просмотра.
- Закрытие сделки не реализовано: кнопка `Закрыть` не переводит в `won/lost`, нет причины отказа.
- Счета/закрывающие документы отсутствуют как рабочий процесс. `Выставить счет` отмечен как этап 2 и не действует.
- КП не отправляется email/Telegram, PDF не скачивается, статусы `viewed/accepted/rejected` только отображаются на mock-данных.

### Тендеры

- `Рассчитать цену`, `Подать заявку`, `Записать результат`, `Закрыть тендер`, `Создать сделку` для выигранного тендера не меняют состояние.
- Расчетные поля во вкладке `Расчет` disabled.
- Календарь тендеров ведет в карточки по чипам, но стрелки месяца не меняют месяц.

### Настройки и отчеты

- CRUD-кнопки в настройках статичные: этапы, шаблоны КП, источники, токены, интеграции не меняются.
- Фильтр периода в отчетах статичный.
- Отчеты строятся по mock-данным; подтвердить управленческую достоверность нельзя без API/БД.

## 5. Источники заявок

В настройках сейчас нет требуемых реальных каналов:

- `spliit-hub.ru`
- приложение Spliit Hub
- `spliithome.ru`
- `klimatsimf.ru`
- Авито

В UI обнаружены только обобщенные/демо-источники: `Сайт основной`, `Сайт opt`, `Telegram-бот`, `Звонок входящий`, `Email-форма`, а в токенах сайтов - `nordlight.ru`, `nordlight-opt.ru`, `nordlight-tenders.ru`, `landing-promo.ru`.

## 6. Что работает визуально

- Основные страницы открываются с HTTP 200.
- Dashboard owner/manager отрисовываются.
- Списки лидов, клиентов, сделок, задач, КП, тендеров показывают mock-данные.
- Карточные вкладки клиента/сделки/сотрудника/тендера переключаются.
- Command palette открывается и ищет по mock-данным.
- Отчеты отрисовывают графики; canvas не пустые.
- Empty-state страницы отображаются.

Это полезно как frontend-прототип, но не является приемкой рабочей CRM.

## 8. Рекомендованный порядок исправления

1. Поднять backend API по спецификации и подключить frontend к `/api`.
2. Реализовать настоящую авторизацию, сессии, logout, server-side permissions.
3. Сделать CRUD для клиентов, лидов, сделок, задач, КП, тендеров с сохранением в БД.
4. Реализовать входящие webhook-источники и завести реальные каналы: Spliit Hub, Spliit Home, KlimatSimf, Авито.
5. Доделать жизненный цикл сделки: этапы, КП, счет, оплата, won/lost, причина отказа, история.
6. Подключить коммуникации: сообщения, SMS, Telegram/email, журнал ошибок отправки.
7. Подключить фильтры, поиски, действия строк, календарную навигацию.
8. Исправить mobile shell и overflow.
9. После исправлений провести повторный end-to-end приемочный прогон с тестовыми ролями и тестовыми заявками с каждого источника.

## 9. Минимальный повторный тест после доработки

Для приемки MVP нужна сквозная проверка:

1. Войти owner/manager/admin с валидным и невалидным паролем.
2. Отправить webhook-заявку от каждого источника.
3. Проверить создание лида, UTM, ответственного, уведомление.
4. Обработать лид, назначить менеджера, перевести в сделку.
5. Создать клиента, контакт, задачу, сообщение.
6. Создать сделку, добавить товары, сменить этапы.
7. Создать КП, PDF, отправить email/Telegram, проверить историю.
8. Выставить счет или явно убрать этот процесс из MVP.
9. Закрыть сделку успешно и отказом с причиной.
10. Проверить отчеты, рабочее время, журнал действий и ограничения ролей.
