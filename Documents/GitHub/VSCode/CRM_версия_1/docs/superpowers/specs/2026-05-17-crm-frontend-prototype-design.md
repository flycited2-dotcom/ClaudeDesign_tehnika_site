# CRM Frontend Prototype — Design Spec

Дата: 2026-05-17
Статус: согласовано пользователем, готово к составлению implementation-плана.

## 0. Контекст и объём

Проект — визуальный frontend-прототип CRM-системы по ТЗ из `crm_project_docs/`. Прототип, **не MVP**:

- только frontend, без бэкенда,
- данные mock-овые, синхронные, в JS,
- все экраны и все вкладки из `07_UI_UX_SPEC.md`,
- обе роли (собственник, менеджер) с переключателем,
- визуальное направление: светлый бизнес-премиум (Notion/Stripe-vibe),
- цель — утвердить визуальный язык и UX до начала полноценной разработки на стеке из `02_ARCHITECTURE.md`.

Противоречие со стеком ТЗ (Next.js/NestJS) на этом этапе сознательно не решается: прототип строится на чистом HTML + Tailwind CDN, как требует `.claude/CLAUDE.md`. Переход на Next.js — задача следующего этапа (MVP) и будет описан отдельным spec'ом.

## 1. Технологический стек

- Чистый HTML (несколько связанных страниц).
- Tailwind CSS через CDN (`<script src="https://cdn.tailwindcss.com">`).
- Ванильный JS — никаких фреймворков, бандлеров, npm-зависимостей фронта.
- Шрифты — Google Fonts: Fraunces (serif), Inter (sans), JetBrains Mono (mono).
- Иконки — lucide через CDN.
- Графики (только в отчётах) — Chart.js через CDN.
- Локальный сервер — существующий `serve.mjs` на `http://localhost:3000`.
- Скриншоты — существующий `screenshot.mjs` (Puppeteer), расширить на 3 разрешения.

Правило `.claude/CLAUDE.md` «один index.html» трактуется как «без сборщика и без фреймворка». При 30+ экранах разделение на файлы — необходимость, не отступление.

## 3. Визуальный язык (фиксируется в `tokens.css`)

### Палитра

- Фон приложения: `#FAFAF7`
- Поверхность карточек: `#FFFFFF`
- Поверхность sidebar: `#F5F4EF`
- Бордер тонкий: `#EBE9E2`
- Бордер контрастный: `#D9D6CC`
- Текст основной: `#1C1B17`
- Текст вторичный: `#6B6862`
- Текст приглушённый: `#9C9890`
- **Акцент бренда:** `#1F4A3A` (deep racing green)
- Акцент-hover: `#163528`
- Акцент-soft: `#E8EFEB`

### Семантика статусов

| Статус | fg | bg |
|---|---|---|
| success / квалифицирован | `#2F7D5C` | `#E6F1EB` |
| warning / в работе | `#B5841E` | `#F7EFDC` |
| danger / просрочка | `#A8392E` | `#F4E4E1` |
| info / новый | `#3A5C8C` | `#E6ECF4` |
| neutral / закрыт/отказ | `#6B6862` | `#EFEDE7` |

Использовать только через семантические токены (`--status-danger-fg/bg`), не цвета напрямую.

### Типографика

- Heading: **Fraunces** (variable serif), tracking `-0.02em` на крупных.
- Body / UI: **Inter** (variable).
- Mono / суммы и id: **JetBrains Mono**, `tabular-nums` для денежных колонок.
- Шкала: 12 / 13 / 14 / 16 / 18 / 22 / 28 / 36 / 48.
- Line-height: 1.5 body, 1.2 large heading, 1.7 long description.

### Spacing, радиусы, тени

- Spacing-шкала: 4 / 8 / 12 / 16 / 20 / 24 / 32 / 48 / 64.
- Радиусы: 6 / 10 / 14 / 999.
- Тени (тёплые, без чистого чёрного):
  - `--shadow-sm`: `0 1px 0 rgba(28,27,23,0.04), 0 1px 2px rgba(28,27,23,0.04)`
  - `--shadow-md`: `0 1px 0 rgba(28,27,23,0.04), 0 4px 12px -2px rgba(28,27,23,0.06), 0 12px 24px -8px rgba(28,27,23,0.05)`
  - `--shadow-lg`: shadow-md + `0 24px 48px -12px rgba(28,27,23,0.08)`.
- Никаких tailwind-`shadow-md` из коробки.

### Декор

- Едва заметный SVG-noise overlay на фоне приложения (opacity ~0.025).
- На дашборде owner — один радиальный градиент в правом-верхнем углу hero-блока (`#E8EFEB` → transparent).

### Состояния и анимации

- Каждый интерактивный элемент: `default → hover → focus-visible → active → disabled`.
- Hover строк таблиц: фон `#F5F4EF`, левый бордер 2px акцентом.
- Focus-ring: 2px `#1F4A3A` offset 2px, browser default отключён.
- Анимации только `transform` и `opacity`, 150–200ms, `cubic-bezier(0.2, 0.8, 0.2, 1)`.
- `transition-all` запрещён.

## 4. Оболочка (shell)

### Принцип инжекции

Каждая страница содержит:

```html
<div data-shell="sidebar"></div>
<div data-shell="topbar"></div>
```

`shell.js` fetch'ит фрагменты, инжектит, помечает активный пункт меню по `data-route` страницы, навешивает переключатель ролей, фильтрует пункты меню по `localStorage.role` (default `owner`).

### Sidebar (248px фикс)

- Лого-блок (высота 64px): «CRM» в Fraunces + подпись компании.
- Группы пунктов с капс-подписями:
  - **РАБОТА**: Рабочий стол, Лиды, Сделки, Задачи
  - **КЛИЕНТЫ И ПРОДАЖИ**: Клиенты, КП, Тендеры
  - **АНАЛИТИКА**: Отчёты
  - **АДМИНИСТРИРОВАНИЕ** (owner only): Сотрудники, Настройки
- Пункт: 36px высота, padding 12px, иконка 18px + label 14px.
- Активный: фон `#E8EFEB`, левая полоса 3px акцентом, текст основной.
- Hover: фон `#EFEDE7`.
- Бэйджи-счётчики справа на пунктах с динамикой (Лиды, Задачи).
- Внизу — карточка статуса рабочего дня: «🟢 На смене с 09:14 · 3ч 26м» + «Завершить день».

### Topbar (64px, sticky)

Слева → направо:
1. Хлебные крошки / название раздела (Fraunces 18px).
2. Глобальный поиск (max-width 480px), плейсхолдер «Найти клиента, сделку, КП, задачу…», подсказка `⌘K`. На фокусе — dropdown с группированными mock-результатами.
3. Spacer.
4. CTA «+ Создать» (акцентный, белый текст) → dropdown: Клиент / Лид / Сделка / Задача / КП.
5. Колокольчик уведомлений (красная точка при непрочитанных) → popover со списком.
6. Сегментированный переключатель `[Собственник | Менеджер]`. Переключение → `localStorage.role` + `location.reload()`.
7. Аватар 32px → popover «Профиль / Настройки / Выйти».

### Контентная область

- Padding `32px 40px`, max-width 1440px по центру.
- Заголовок экрана: H1 (Fraunces 28px) + подпись `text-secondary` + правая зона действий (фильтры/импорт/экспорт). Высота 80px, нижний тонкий бордер.

### Адаптивность

- <1280px: sidebar → icon-rail 64px.
- <900px: sidebar → off-canvas, гамбургер в topbar.
- Десктоп — приоритет; мобильный layout не должен ломаться, но не оптимизируется.

### Что меняется при смене роли

| Элемент | owner | manager |
|---|---|---|
| Меню «Сотрудники», «Настройки» | видны | скрыты |
| Home после логина | `dashboard-owner.html` | `dashboard-manager.html` |
| Tasks default tab | «Все задачи» | «Мои задачи» |
| Deals default filter | без фильтра | префильтр «Мои» |
| KPI на дашборде | управленческие (ТЗ §4) | личные (ТЗ §5) |

## 5. Mock-данные

Один файл `assets/js/mock-data.js`, экспортирует `window.MOCK`. Все коллекции синхронные.

### Коллекции

```
MOCK.users         — 8 сотрудников (1 owner, 1 РОП, 4 менеджера, 1 тендерный спец, 1 закупщик)
MOCK.clients       — 24 клиента (B2B-уклон: опт, торговые сети, госы, ИП)
MOCK.contacts      — 40 контактов, привязка к clients
MOCK.leads         — 18 лидов, разные статусы, часть «висит >15 мин»
MOCK.deals         — 22 сделки в 5 этапах, 80k–4.2M ₽
MOCK.dealProducts  — товарные строки сделок
MOCK.tasks         — 35 задач: текущие, завтрашние, просроченные, выполненные
MOCK.offers        — 12 КП в draft/sent/viewed/accepted/rejected
MOCK.tenders       — 6 тендеров: 2 горящих, 1 выигран, 1 проигран, 2 в работе
MOCK.messages      — 15 последних сообщений (telegram/email/внутренний)
MOCK.notifications — 8 уведомлений в колокольчике
MOCK.workSessions  — журнал входов/выходов за неделю
MOCK.activity      — лента истории действий (функция по entity_id)
```

### Правдоподобие

- Реальные русские названия: «ТД Северное Сияние», «Промлогистик-Урал», «ГБУЗ ГКБ №67», «ИП Корнилова О.А.».
- Реальные ФИО.
- Аватары — инициалы на цветной подложке (детерминированно из хэша имени).
- Суммы: рубли, разряды через тонкий пробел `1 240 000 ₽`.
- Даты — ISO в mock, в UI относительные («3 ч назад», «завтра 10:00»). Хелпер `formatRelative(iso)` в `relative-date.js`. Все даты генерируются от «сегодня».
- Источники лидов: «Сайт основной», «Сайт opt», «ZakupKi», «Telegram-бот», «Звонок входящий».
- Этапы воронки — из ТЗ/business-processes, не «New/In Progress».
- Распределение неравномерное, проблемные зоны для дашборда owner: 3 лида «без обработки >15 мин», 4 просроченных задачи, 2 «без движения >3 дней» сделки, 1 тендер «<48 ч».

### Связность

- ID — строки (`CL-0001`, `DL-0014`, `TS-0033`), отображаются как чипы.
- Связи через `client_id` / `responsible_id`, никакой денормализации.

### Хелперы рендера (`widgets.js`)

- `renderTable(selector, config)` — таблица: колонки, визуальная сортировка, zebra, hover, empty-state.
- `renderKanban(selector, columns, cardsByColumn, cardRenderer)`.
- `renderKpiCard(value, label, delta, trend)`.
- `renderBadge(status)` — по семантическому ключу.
- `renderAvatar(name)`.
- `renderTabs(tabs, activeId)`.

## 6. Порядок сборки (батчи)

Подход — style-first. Между батчами — обязательные стопы для согласования. После батча 1 стиль зафиксирован и не пересматривается.

**Батч 0 — Фундамент.** `tokens.css`, `app.css` (`.btn-primary/.btn-secondary/.btn-ghost`, `.card`, `.surface`, `.input`, `.badge-*`, `.tab-bar`, `.table-app`), пустой `shell.js`, заполненный `mock-data.js`, подключение шрифтов и иконок.

**Батч 1 — Эталон: Дашборд собственника.** ⭐ Точка фиксации стиля.
- Полная оболочка + hero + 7 KPI + «Проблемные зоны» + таблица сотрудников + right-rail.
- **Стоп. Утверждение визуального языка.** Скриншоты × N, итерации.

**Батч 2 — Дашборд менеджера + Логин.**
- `dashboard-manager.html` по ТЗ §5.
- `login.html` без shell: слева форма, справа фирменный визуал (off-white + радиальный градиент + Fraunces).

**Батч 3 — Списковые экраны.**
- Клиенты (список+фильтры), Лиды (список+канбан), Сделки (канбан/таблица/by-client), Задачи (5 представлений), КП (список), Тендеры (список+календарь).

**Батч 4 — Карточки сущностей.**
- Клиент (8 вкладок), Сделка (7 вкладок), КП (превью PDF inline), Тендер.
- Максимум плотности: timeline, чат-лента, файловые превью, активити-лог.

**Батч 5 — Отчёты, Сотрудники, Настройки** (owner-only).
- Отчёты — 7 экранов из ТЗ §14, Chart.js под токены.
- Сотрудники — таблица + карточка с KPI/журналом/задачами/КП.
- Настройки — воронки, шаблоны КП, источники лидов, токены сайтов, интеграции (заглушки с описаниями).

**Батч 6 — Оверлеи и состояния.**
- 4 модалки создания (фрагменты в `/app/shell/modals/`, инжектятся `shell.js` при первом открытии).
- Финал popover'ов уведомлений/профиля.
- `⌘K` командная палитра.
- Empty-states для всех списков.
- Skeleton/loading-states на ключевых экранах.
- 404 в бренде.

Распределение усилий: Б0 ~5%, Б1 ~25%, Б2 ~8%, Б3 ~20%, Б4 ~25%, Б5 ~12%, Б6 ~5%.

## 7. Workflow проверки

### Сервер

- `node serve.mjs` один раз в фоне в начале сессии, http://localhost:3000.
- Если уже запущен — не запускать второй инстанс.
- Все скриншоты — с localhost, никогда с `file:///`.

### Скриншот-цикл для каждого готового экрана

1. `node screenshot.mjs http://localhost:3000/app/<page>.html <label>`.
2. PNG → `./temporary screenshots/screenshot-N-<label>.png` (auto-increment).
3. Прочитать через Read tool, проанализировать визуально.
4. Сравнить с эталоном (батч 1) по конкретным метрикам:
   - spacing вокруг карточек (32/40 px),
   - вес/размер заголовков,
   - акцентный цвет не «уехал»,
   - тени-sm на карточках,
   - hover на интерактивных.
5. Описать отличия конкретно, починить, переснять.
6. **Минимум 2 круга** на экран. Стоп только при отсутствии отличий или явном «достаточно» от пользователя.

### Разрешения

- 1920×1080 — основной кейс.
- 1366×768 — нижняя граница comfort-десктопа.
- 768×1024 — планшет, проверка off-canvas sidebar.

В батче 0 расширить `screenshot.mjs` поддержкой аргумента разрешения (если ещё не поддерживает).

### Чеклист приёмки экрана

- [ ] Скриншоты в 3 разрешениях, layout не сломан.
- [ ] Все интерактивные имеют `:hover` и `:focus-visible`.
- [ ] Нет tailwind-default-палитры (`indigo`, `blue-500`, `green-500`, ...) — проверять grep'ом.
- [ ] Нет `transition-all`.
- [ ] Суммы в `tabular-nums`, в рублях, с разрядами.
- [ ] Статусы через семантические классы.
- [ ] Empty-state нарисован (если список).
- [ ] Skeleton-state нарисован на ключевых экранах.

### Регрессия

После любой правки `tokens.css` или `app.css` после батча 1 — переснимаются ВСЕ существующие экраны и проводится визуальная сверка. Это удерживает соблазн «ещё чуть-чуть подкрутим базовый цвет».

### Финальная приёмка прототипа

- Полный набор скриншотов всех экранов в 1920×1080.
- Демо-флоу: login → owner dashboard → role switch → deals kanban → deal card → create-offer modal → back to dashboard.

## 8. Что НЕ входит в этот прототип

- Любой backend-код, БД, миграции, API.
- Любые реальные интеграции (Telegram, 1С, SMTP, S3, сайт-webhook).
- Авторизация (login.html — только визуал формы, никакой логики).
- Реальное сохранение данных (любые «Создать» — модалка показывается, на «Сохранить» закрывается, ничего не пишется).
- Тесты.
- Сборка/деплой/CI.
- Адаптация под мобильные ниже планшета.
- Стек ТЗ (Next.js/NestJS) — отдельный этап после утверждения визуала.
