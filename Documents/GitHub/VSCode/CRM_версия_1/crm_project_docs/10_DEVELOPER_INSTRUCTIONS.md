# Инструкции разработчикам CRM

## 1. Главная цель разработки

Создать не универсальную CRM, а внутреннюю операционную систему компании для управления клиентами, заявками, сделками, задачами, КП, коммуникациями, сотрудниками и будущими интеграциями.

## 2. Что нельзя делать

Нельзя:

- превращать CRM в замену 1С;
- делать складской монстр на первом этапе;
- хардкодить роли;
- хардкодить статусы без справочников там, где нужна гибкость;
- хранить файлы в базе;
- пропускать audit log для важных действий;
- делать бизнес-логику на frontend;
- делать интерфейс без учета ролей;
- удалять данные физически;
- начинать с AI, MAX, WhatsApp или сложной 1С-интеграции.

## 3. Что важно сделать качественно

Приоритет:

1. Роли и права.
2. Лиды.
3. Задачи.
4. Сделки.
5. КП.
6. Уведомления.
7. Рабочее время.
8. Дашборд собственника.

## 4. Кодовая архитектура

Backend:

- NestJS modules;
- services для бизнес-логики;
- controllers только для API;
- DTO для валидации;
- guards для прав;
- repositories/ORM слой для данных;
- events для уведомлений;
- queues для фоновых задач.

Frontend:

- Next.js App Router;
- TypeScript;
- компонентная структура;
- отдельные страницы по модулям;
- общие компоненты таблиц, карточек, форм, модалок;
- guard маршрутов по роли.

## 5. Соглашения по статусам

Статусы должны быть кодовыми значениями в базе и отображаться русскими названиями в интерфейсе.

Пример:

- new → Новый
- in_progress → В работе
- completed → Выполнено
- overdue → Просрочено

## 6. Логирование

Все важные действия писать в activity_logs:

- создание;
- изменение;
- удаление;
- смена статуса;
- отправка КП;
- назначение ответственного;
- вход;
- выход;
- ошибка интеграции.

## 7. Уведомления

Не отправлять уведомления напрямую из разных модулей.

Правильно:

1. Модуль создает событие.
2. NotificationService принимает событие.
3. NotificationService решает, кому отправить.
4. Канальные адаптеры отправляют сообщение.

## 8. Проверка перед сдачей каждого этапа

Перед передачей этапа разработчик обязан проверить:

- миграции применяются на чистой базе;
- seed-данные создаются;
- роли работают;
- API документирован;
- frontend не падает;
- основные сценарии проходят вручную;
- ошибки отображаются понятно;
- нет критичных console errors;
- нет открытых секретов в репозитории.

## 9. Минимальный seed

Создать стартовые роли:

- owner;
- manager_head;
- manager;
- accountant;
- admin.

Создать стартового пользователя owner.

Создать базовые статусы:

- лиды;
- задачи;
- сделки;
- КП;
- тендеры.

## 10. Первая версия интерфейса

Не нужно делать дизайнерский шедевр на MVP. Главное:

- быстро;
- понятно;
- таблицы читаемые;
- карточки удобные;
- кнопки очевидные;
- просрочки заметны;
- собственник видит контроль.

## 11. Контроль качества

Каждый pull request должен проверяться по пунктам:

- нет нарушения прав доступа;
- нет потери данных;
- нет SQL-инъекций;
- нет открытых endpoint без авторизации;
- есть валидация входных данных;
- есть обработка ошибок;
- есть audit log для критичных действий.
