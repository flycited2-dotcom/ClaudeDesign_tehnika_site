# Быстрый поиск с локальным словарём и прогревом

## Цель

Сделать поиск по всему каталогу быстрым для частых запросов и понятным для разговорных русскоязычных форм без внешних SEO-баз, API и миграций базы данных.

## Границы

- Покрываем поиск товаров на `/search` и быстрые подсказки в шапке.
- Используем только локально поддерживаемый словарь, существующий каталог и уже собираемую статистику поиска.
- Не пытаемся прогреть все категории, товары или возможные слова: это создало бы лишнюю нагрузку и не улучшило бы первое впечатление пользователя.
- Не меняем модель Prisma и не меняем существующую схему учёта поисковых запросов.

## Подход

### 1. Единый словарь

Новый модуль хранит два неизменяемых набора данных:

- `aliases`: разговорные, сокращённые и распространённые варианты товарных названий. Примеры: `телик` и `тв` → `телевизор`, `стиралка` → `стиральная машина`, `ноут` → `ноутбук`, `кондер` → `кондиционер`, `айфон` → `iphone`.
- `seedQueries`: ограниченное ядро канонических широких товарных запросов, распределённых по основным разделам каталога. Эти фразы одновременно служат стартовыми подсказками и целями прогрева.

Модуль экспортирует чистую функцию нормализации. Она приводит пробелы и регистр к стабильному виду и заменяет только полные слова/фразы из словаря. Бренды, модели, артикулы и незнакомые слова остаются без изменений: например, `телик Samsung QE55` становится `телевизор samsung qe55`.

### 2. Поисковый путь

Страница поиска сохраняет введённую пользователем фразу для заголовка и аналитики, но передаёт нормализованную фразу в каталоговый поиск. Таким образом разные варианты одного намерения используют одну и ту же запись `unstable_cache` выдачи.

Маршрут `/api/search/suggest` также применяет нормализацию и оборачивает запрос шести товарных подсказок в короткий серверный кэш. В результате ввод `телик`, `тв` и `телевизор` ищет и кэширует одну каноническую выдачу.

### 3. Подсказки до ввода

Шапка получает популярные поисковые фразы с сервера. Когда накопленных запросов ещё мало, она дополняет их `seedQueries`, исключая дубли. По мере работы сайта реальные запросы попадают выше стартовых; пользователю не показываются технические ключи и повторяющиеся фразы.

Для списка не требуется новый API: серверный компонент шапки передаёт готовый список в клиентский `HeaderSearchControl`.

### 4. Прогрев

Новый `scripts/warm_search.sh` получает базовый URL из `WARM_CACHE_BASE` (по умолчанию `https://climat-simf.ru`) и по очереди запрашивает для `seedQueries`:

1. `/search?q=канонический_запрос` — кэш выдачи каталога;
2. `/api/search/suggest?q=канонический_запрос` — кэш быстрых подсказок.

Скрипт использует `flock`, не запускает параллельные HTTP-запросы, пишет только ошибки и подходит для cron. Пример crontab запускает его раз в восемь минут: это соответствует десятиминутному TTL кэша выдачи, не конкурируя с ночной синхронизацией и общим прогревом категорий.

## Производительность и безопасность

- Нормализация — локальная обработка строк; она не обращается к БД и не добавляет сетевой вызов.
- Прогрев ограничен компактным ядром, а не всем каталогом из сотен тысяч товаров.
- Все маршруты сохраняют текущую деградацию при недоступной БД: поиск и подсказки возвращают пустой результат, а не ошибку пользователю.
- Статистика по-прежнему сохраняет исходную поисковую фразу, чтобы администратор видел реальные формулировки и мог расширять словарь осознанно.

## Проверка

Автоматические тесты докажут, что словарь заменяет варианты целыми словами, не портит модель/артикул, и дедуплицирует стартовые/реальные подсказки. Тесты маршрута проверят, что API подсказок использует канонический запрос. Скрипт прогрева проверяется подменой `curl` на тестовый исполняемый файл: он должен вызывать оба маршрута для каждого seed-запроса, корректно URL-кодировать кириллицу и завершаться с ошибкой при не-200 ответе.
