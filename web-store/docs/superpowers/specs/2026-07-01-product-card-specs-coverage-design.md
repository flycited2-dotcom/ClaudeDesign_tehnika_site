# Характеристики на карточке товара — расширение покрытия (ROADMAP #3)

Дата: 2026-07-01

## Контекст

`ROADMAP.md` Tier 1 #3: «У многих товаров спеки бедные/отсутствуют — покупатель не
может выбрать/сравнить». Карточка товара (`app/product/[slug]/page.tsx`) уже строит
блок «Характеристики» через `buildProductFacts()` (`lib/product-display.ts`),
который объединяет три источника: структурные `ProductAttribute` (бэкфилл из
`product-attributes.ts`), live-парсинг названия (`extractProductNameSpecs`,
тот же экстрактор) и статичные поля (SKU/категория/бренд/партномер/гарантия/вес/
кратность/срок поставки — эти всегда присутствуют).

Поставщик (`ItpProduct`, `lib/itp/types.ts`) не отдаёт вообще никакого поля с
характеристиками — только `barcodes/category/name/part/vendor/volume/warranty/
weight`. Единственный источник технических специй — парсинг названия товара.
«Чистый источник спеков» от поставщика физически недоступен.

## Данные (прод, read-only psql, 2026-07-01)

Из 249 524 продаваемых товаров (`isActive && isVisible && retailPrice > 0`):
- **98 522 (39.5%)** — 0 строк в `ProductAttribute` (только административные поля).
- **112 492 (45%)** — 1-2 атрибута.
- Только **38 510 (15.4%)** имеют 3+ атрибута.

Разброс по категориям неравномерный. Категории вида «Картриджи для оргтехники»/
«Чипы»/«Дисплеи» (запчасти/расходники) названы голыми моделями — там реально
нечего извлекать, это не в скоупе. Отобраны 5 категорий с максимальным ROI
(большой объём + название содержит парсибельный текст, не только модель):

| Категория | Всего | Бедных (≤1 атрибут) | % |
|---|---|---|---|
| Розетки, выключатели и рамки | 14 915 | 7 290 | 48.9% |
| Встраиваемые варочные панели | 1 336 | 1 159 | 86.8% |
| Проводные роутеры/коммутаторы | 1 463 | 1 273 | 87.0% |

## Архитектура (не меняется)

`lib/product-attributes.ts` — набор gated-функций `extractXAttributes(text, attrs)`,
каждая начинается с `if (!looksLikeX(text)) return;`. Новые категории добавляются
как новые функции/ветки, существующие регексы не трогаем (защита от регрессий —
уже дважды ловили межкатегорийные коллизии: `power_hp` на «10 л, сенсор»,
`smart_tv` на не-телевизорах).

`lib/catalog-attribute-registry.ts` — реестр ключей (`catalogAttributeDefinitions`)
+ маппинг категория→семейство (`getCatalogAttributeFamilyForCategory`). Новые ключи
здесь автоматически становятся фильтрами в панели каталога — бонус без доп. работы.

`lib/product-display.ts` — `productAttributeFactOrder` определяет порядок вывода
на карточке товара; новые ключи добавляются в массив.

## Изменения по категориям

### 1. Розетки, выключатели, рамки (семейство `electrical`, уже существует)

- **Баг:** `ip_rating` числится в реестре для `electrical` (`families: ["electrical", "garden", "camera"]`),
  но извлекается только внутри `extractCameraAttributes`. Для электрики код никогда
  не вызывается. Фикс: вынести `extractIpRating(text): {value,normalizedValue} | null`
  в отдельную функцию, вызывать из camera- и из electrical-экстрактора.
- Новый ключ `mount_type` (Установка: Открытая/Скрытая) — паттерны только полными
  словоформами: `открыт[а-яё]*\s+установ|наружн[а-яё]*\s+установ` → «Открытая»,
  `скрыт[а-яё]*\s+установ|внутренн[а-яё]*\s+установ` → «Скрытая». **Не используем**
  двухбуквенные аббревиатуры (ОП/СП/ОУ/СУ) — риск коллизий как с л.с./smart_tv.
- Новый ключ `gang_count` (Количество клавиш/постов) — `(\d)[\s-]*(?:кл(?:авиш)?[а-яё]*\b)`
  и `(\d)[\s-]*пост` (посты рамок).
- `extractColor`: добавить Мокко/Шампань/Слоновая кость/Айвори/Графит (частые
  финиши в этой категории, отсутствуют в текущем словаре).
- `extractElectricalProductType`: добавить «Рамка» (`рамк`), «Переключатель»
  (`переключател`, отдельно от «выключатель»), «Терморегулятор» (`терморегулятор`).

### 2. Встраиваемые варочные панели (семейство `appliance`, ключи уже есть) — чистый bugfix

Тот же класс бага, что уже чинили для «духовой шкаф» (JS `\w` не матчит кириллицу):
гейт `extractCooktopAttributes` — `/варочн\w*\s*(?:панел|поверхн)/i` — матчит только
голое «варочн» вплотную к «панел»/«поверхн», никогда не матчит «варочн**ая**
панель». Фикс: `варочн[а-яё]*\s*(?:панел|поверхн)`. Один regex-символ, но должен
закрыть большую часть из 1159 «бедных» — `cooktop_type`/`burner_count`/`width_cm`
уже есть в реестре и корректно парсятся, просто гейт их не пускал.

### 3. Проводные роутеры/коммутаторы — новое семейство `network`

Категория сейчас не матчится ни в одно семейство (`getCatalogAttributeFamilyForCategory`
возвращает `null` → только universal-цвет). Добавить:
- `CatalogAttributeFamily` union: `"network"`.
- Маппинг: `/роутер|маршрутизатор|коммутатор|switch|router/` → `"network"`.
- Ключи: `port_count` (Количество портов, число перед «порт[а-ов]*»),
  `poe_support` (boolean, `\bpoe\b`), `managed_type` (enum: Управляемый/
  Неуправляемый — литеральные слова `управляем[а-яё]*` с отрицанием
  «не» спереди для «Неуправляемый»).

### 4. Камеры видеонаблюдения (семейство `camera`, уже существует)

- `camera_lens_mm`: сейчас требует слово «объектив»/«фокус» рядом с числом —
  в CCTV-названиях фокусное расстояние часто голое число («3.6-3.6мм»). Добавить
  альтернативный паттерн `(\d+(?:[.,]\d+)?)\s*-\s*\d+(?:[.,]\d+)?\s*мм` (диапазон,
  берём первое число) — **только внутри `extractCameraAttributes`** (уже gated
  по `looksLikeCameraProduct`), не трогая общий `extractDimensionsCm`.
- Новый ключ `camera_type` (enum: Купольная/Цилиндрическая/Поворотная) —
  `купол|dome`, `цилиндр|bullet`, `поворотн|ptz`.
- Новый ключ `night_vision` (boolean) — `ик[\s-]*подсветк|night\s*vision`.
- `ip_rating` уже извлекается в этой функции — без изменений.

### 5. Кулеры/охлаждение ПК (семейство `computer`, уже матчится, ключей под кулеры нет)

Гейт `looksLikeCoolingProduct(text)` = `/куллер|кулер|охлажден[а-яё]*\s+(?:для\s+)?(?:процессор|пк|computer)|вентилятор\s+корпусн|система\s+охлажден/i`.
- `fan_size_mm` — `(\d{2,3})\s*мм` (первое совпадение; гейт уже сужает контекст
  до охлаждения, коллизия с другими размерами маловероятна).
- `noise_db` — `(\d+(?:[.,]\d+)?)\s*дБ[а]?`.
- `rpm` — `(\d+)(?:-(\d+))?\s*(?:об/?мин|rpm)` — если диапазон, берём верхнюю границу.
- `has_argb` (boolean) — `\bargb\b|\brgb\b` (без ложного срабатывания на «без подсветки» — негативная проверка `без\s+(?:argb|rgb|подсветк)` исключает).

## Тестирование

Guard-тесты в `product-attributes.test.ts` для каждого нового паттерна:
позитивный кейс (реальное название из прод-выборки) + минимум один негативный
(соседняя категория, которая НЕ должна получить этот атрибут — по образцу
существующих guard-тестов на `power_hp`/`smart_tv`).

`npm run lint && npm run test && npm run build` перед деплоем — обязательно
(build ловит RSC/TS-ошибки, которые lint+test пропускают).

## Раскатка и верификация

1. Деплой кода (`deploy_vps.py`).
2. `npm run sync:attributes` бэкфилл на VPS (пересчитывает `ProductAttribute`
   для всего каталога, ~340k товаров, уже проверенная операция из Iter 61-62).
3. Верификация теми же psql-запросами, что использовались для скоупинга
   (poor_pct по каждой из 5 категорий, до/после) — по цифрам, не на глаз.
4. Смоук прод-страниц: по одному товару из каждой категории на `/product/<slug>`
   — блок «Характеристики» содержит новые поля.

## Риски / границы

- **Не трогаем** ~66k товаров категорий-расходников (картриджи/чипы/дисплеи-запчасти) —
  их названия не содержат парсибельного текста, это осознанно вне скоупа
  (остаётся долгом в ROADMAP).
- Аббревиатуры (ОП/СП/ОУ/СУ, "мм" без контекста и т.п.) намеренно не парсим —
  риск коллизий важнее полноты покрытия.
- Бэкфилл `sync:attributes` идемпотентен (уже использовался 3 раза), но проходит
  по всему каталогу — не мгновенный (предыдущий прогон: 340 747 scanned).
