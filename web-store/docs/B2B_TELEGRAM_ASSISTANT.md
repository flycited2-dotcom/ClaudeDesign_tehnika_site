# Мобильный B2B-ассистент

Отдельный Telegram-процесс использует общую PostgreSQL-базу сайта и существующие интеграции I-T-P. Поиск не вызывает API поставщика на каждый запрос: он работает по локально синхронизированному каталогу, поэтому отвечает быстро и не расходует лимит `get_active_products`.

## Что реализовано в первом срезе

- приватный доступ по allow-list Telegram ID;
- поиск по названию, модели, бренду, штрихкоду и SKU;
- ранжирование точного SKU/артикула выше общего совпадения;
- отдельные менеджерские карточки с закупочной ценой, остатком и заказом;
- пресеты и ручной ввод наценки;
- клиентские карточки без закупочной цены, поставщика и внутреннего SKU;
- подписанное предложение с фиксированной клиентской ценой и сроком действия;
- inline-отправка карточки в любой выбранный Telegram-чат;
- сохранение polling offset и автоматический перезапуск через systemd.

## Настройка нового Telegram-бота

1. Создать отдельного бота через `@BotFather`.
2. Выполнить `/setinline`, выбрать нового бота и указать placeholder, например `Введите модель товара`.
3. Узнать собственный числовой Telegram user ID и добавить его в `B2B_ASSISTANT_TELEGRAM_USER_IDS`.
4. Сгенерировать отдельный случайный `B2B_ASSISTANT_OFFER_SECRET` длиной не менее 32 символов.
5. Заполнить переменные `B2B_ASSISTANT_*` в серверном `.env` и установить сервис.

```bash
sudo bash scripts/install-b2b-assistant-systemd.sh
journalctl -u climat-simf-b2b-assistant -f
```

Нельзя одновременно запускать webhook или второй polling-процесс с токеном этого бота. Сервис при старте удаляет webhook и становится единственным потребителем `getUpdates`.

## Пользовательский сценарий

1. Менеджер отправляет боту `Lenovo IdeaPad 16 512` или точный SKU.
2. Бот показывает до пяти менеджерских карточек.
3. Кнопка `Заказать` открывает существующую подписанную форму заказа с повторной проверкой остатка.
4. Кнопка `Клиенту +15%` или `Своя наценка` создаёт очищенную клиентскую карточку.
5. Кнопка `Отправить клиенту` переводит менеджера в inline-режим и предлагает выбрать чат.

Inline-запрос также можно начать вручную: `@имя_бота модель`. В этом случае применяется `B2B_ASSISTANT_DEFAULT_MARKUP_PERCENT`.

## Границы первого среза

В наблюдение, избранное, история заказов, индивидуальные наценки по категориям и несколько ролей будут добавляться поверх этого процесса. Заказы по-прежнему не подтверждаются на отгрузку автоматически.

## Закупка списком из файла

Импорт работает в обоих существующих процессах: боте мониторинга/заказов
(`stock-order-bot`) и мобильном B2B-ассистенте. Отдельный бот не нужен.
Категория товара не ограничена: картриджи, кабели, техника и другие товары
поставщика проходят один и тот же сценарий.

1. Отправить боту `.xlsx` или CSV в UTF-8 размером до 5 МБ.
2. Если в книге несколько подходящих листов, выбрать **один**. Листы не
   суммируются: сводка и раскладка по ТЗ могут описывать одну закупку.
3. Получить CSV-отчёт с исходными количествами, текущими ценами и остатками API.
4. Нажать «Создать весь заказ B2B» под отчётом выбранного листа.
5. Получить номер одного заказа и завершить работу с ним в портале поставщика.

Колонки определяются по заголовкам в первых 100 строках. Рекомендуемый формат:

| Артикул поставщика | Наименование | Количество |
| --- | --- | --- |
| 12345678 | Название товара | 10 |

Поддерживаются также заголовки `SKU`, `Артикул IT Partner`, `Модель / Part#`,
`Артикул`, `Бренд`, `К заказу, шт.`, `Кол-во, шт.`, `Примечание`. Заголовки не
зависят от регистра. Для CSV поддерживаются разделители `;`, `,` и табуляция.
Артикулы сохраняются текстом, включая ведущие нули. Формулы в идентификаторах
и количествах не выполняются и не принимаются как закупочные данные.

Точный **SKU поставщика** используется напрямую, даже если локальный каталог
ещё не синхронизирован. Для артикула производителя или названия требуется
единственное точное совпадение в локальном каталоге; при неоднозначности бот
просит указать SKU. Автоподмена товара аналогом не выполняется.

Повторяющиеся SKU объединяются **внутри выбранного листа**, количества
суммируются. Допускается до 500 товарных строк на листе, до 10 000 единиц
одного SKU, до 20 листов в книге. Любая ошибка товарной строки останавливает
подготовку заказа всего листа: строки не пропускаются молча.

### Полные количества и наличие

По выбранному владельцем сценарию остатки носят информационный характер.
Нулевой остаток, нехватка, отсутствие точного количества, кратность или ошибка
проверки наличия **не уменьшают и не исключают** позиции. Значения `*`, `**`,
`***` показываются как категории наличия и не переводятся в выдуманное число.
Старые цены из Excel не передаются поставщику как актуальные.

Заказ создаётся с `without_reserve: true`, без подтверждения отгрузки.
Это позволяет запросить полный список для последующей работы в B2B. Сам
поставщик всё ещё может отклонить товар/количество: бот проверяет сохранённые
позиции и сообщает о незавершённом заполнении, указывая номер заказа. При
повторе используется этот же номер. Полный успех сообщается только после
проверки каждого SKU и его количества через API.

### Установка обновления

После получения кода в корне `web-store`:

```bash
npm ci
npx prisma generate
npx prisma db push --skip-generate
npm run build
sudo systemctl restart climat-simf-stock-order-bot
sudo systemctl restart climat-simf-b2b-assistant
```

Перезапускать нужно только установленные сервисы. Если используется webhook
бота заказов, обновить и перезапустить веб-приложение вместо polling-сервиса.
Не запускать второй потребитель `getUpdates` с тем же токеном.

Новые секреты не требуются: используются существующие реквизиты Telegram,
I-T-P и PostgreSQL. Доступ наследуется от каждого бота; для бота заказов
проверяются разрешённый чат и `STOCK_ORDER_TELEGRAM_USER_IDS`, для ассистента —
личный чат и `B2B_ASSISTANT_TELEGRAM_USER_IDS`.

Импорт и выбранные количества хранятся в таблице `TelegramPurchaseImport`.
Кнопки создания действуют 24 часа. Повторная доставка одного Telegram update,
повторные нажатия и перезапуск процесса используют ту же запись. Старые
записи с номером заказа остаются для восстановления результата. Если ответ
на создание потерян до сохранения номера, автоматический повтор запрещён:
бот просит проверить портал, чтобы не создать дубликат. Повторная самостоятельная
отправка файла считается **новой** закупкой.

Исходные пользовательские файлы в репозиторий не добавляются. Данные из
примечаний сохраняются как текст отчёта и не исполняются как команды.
